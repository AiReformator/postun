# 04. Postun Beta — развёртывание и самостоятельный хостинг

Документ описывает, как устроено развёртывание Postun, какие границы доверия соблюдают CI и preview, как вести миграции и откат и как поднять собственную копию сервиса. Пошаговые команды — в [DEPLOY_RUNBOOK.md](DEPLOY_RUNBOOK.md). Живой статус функций — `apps/web/status.json` (на сайте: https://postun.org/#status).

## 1. Принципы

- Код, тесты, CI и шаблоны конфигурации публичны. Реальные идентификаторы ресурсов, секреты и ключи в репозиторий не попадают: `wrangler.jsonc` содержит только заглушки вида `REPLACE_WITH_…`, а подстановка выполняется локально (например, в файле `wrangler.private.jsonc`, который исключён из Git).
- Настройки безопасности по умолчанию одинаковы для размещённого сервиса и для self-host. Бесплатный код не зависит от закрытых сервисов автора.
- Каждая среда (dev, staging, production) использует отдельные ресурсы, данные и ключи.
- Нельзя ради раннего запуска открывать MCP без аутентификации или отключать проверки.

## 2. Адреса

Имена по умолчанию заданы в `wrangler.jsonc` приложений. Для своей установки замените их на домены в вашей зоне (`<your-domain>`).

| Адрес по умолчанию | Назначение | Приложение |
|---|---|---|
| https://postun.org | Публичный лендинг и документация (Workers static assets) | `apps/web` |
| https://app.postun.org | Пользовательский кабинет из той же сборки | `apps/web` |
| https://auth.postun.org | Telegram-вход и OAuth Postun | `apps/auth` |
| https://mcp.postun.org/mcp | Streamable HTTP MCP | `apps/mcp` |
| https://admin.postun.org | Административная часть за OIDC-провайдером администраторов | `apps/admin` |

Для staging в конфигах предусмотрены отдельные имена (`auth.staging.<your-domain>`, `mcp.staging.<your-domain>` и т. д.; для админки `admin-staging.<your-domain>`; Workers с суффиксом `-staging`).

DNS: перед привязкой custom domain сохраните текущие записи зоны (NS, MX, TXT, CAA, A/AAAA/CNAME) и не меняйте почту и посторонние записи. Для apex нужна именно привязка custom domain в Cloudflare (`routes` с `custom_domain: true`); одной DNS-записи CNAME недостаточно. Конфликтующая существующая запись на том же имени должна быть удалена заранее. [S14]

## 3. Токены и секреты

- Разделяйте bootstrap и обычный deploy. Для создания ресурсов и привязки доменов нужен токен с правами на Workers Scripts, Workers KV Storage, D1 (Edit) и на DNS/Workers Routes в нужной зоне; для обычного deploy права на DNS не нужны. Токены создавайте с минимальными правами, ограниченным сроком и без права выпускать новые токены; Global API Key не используйте. Не расширяйте права «для удобства» на все зоны аккаунта.
- Токен Cloudflare передаётся в `npx wrangler` через переменную окружения `CLOUDFLARE_API_TOKEN` из вашего защищённого хранилища, а не аргументом команды.
- Runtime не содержит токена управления Cloudflare. Секреты не передаются в аргументах командной строки, артефактах сборки, публичных issue, файлах `.env` в Git и логах CI.
- Секреты Workers задаются командой `npx wrangler secret put NAME` (значение вводится скрытым вводом или читается из stdin). Для локальной разработки используется `.dev.vars` (в Git не попадает); образцы — `.dev.vars.example` в каталоге приложения.
- Автоматические деплои из GitHub: проверьте фактические права, которые выдаёт платформа, и доступность секретов для сборок. Нативная интеграция сама по себе не делает безопасным любой PR. [S15]

Секреты по Workers (значения — только в Cloudflare Secrets):

| Worker | Секреты |
|---|---|
| `postun-auth` | `TELEGRAM_OIDC_CLIENT_ID`, `TELEGRAM_OIDC_CLIENT_SECRET`, `IDENTITY_INDEX_HMAC_KEY`, `IDENTITY_ENCRYPTION_KEY`, `WEB_SESSION_KEY`; необязательный `BETA_TESTER_TELEGRAM_IDS` |
| `postun-mcp` | `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `SESSION_KEK`, `SESSION_KEK_VERSION`, `CURSOR_HMAC_KEY`; при ротации ключа — `SESSION_KEK_PREVIOUS`, `SESSION_KEK_PREVIOUS_VERSION` |
| `postun-admin` | `ADMIN_OIDC_CLIENT_SECRET`, `ADMIN_SESSION_KEY` (остальные `ADMIN_OIDC_*` — см. раздел 6) |

Ключи шифрования — 32 случайных байта в base64/base64url; генерируются локально и передаются в `wrangler secret put` через stdin.

## 4. Последовательность развёртывания

1. **Основа.** Проверьте версии зависимостей и lockfile, состояние DNS, план Cloudflare и наличие OIDC-провайдера для администраторов. Заполните шаблон `templates/deployment-inventory.example.json` вашими нефиксируемыми в Git идентификаторами.
2. **Проверка Telegram-слоя.** До крупной UI-работы проверьте MTProto-адаптер в настоящем Workers runtime: QR-вход, 2FA (если включена), сохранение шифротекста, холодный перезапуск, чтение собственного тестового диалога и небольшого файла; измерьте CPU, длительность и память. Моки годятся для contract tests, но не заменяют проверку против Telegram.
3. **Защищённая основа.** `postun-auth` + `postun-mcp` (Durable Object `SessionAndQuotaDO`) + Control D1 + OAuth KV; отдельно `postun-admin` + Admin D1 + OIDC-провайдер администраторов. Лимиты и серверные проверки прав включены по умолчанию. Реальные данные размещаются только в привязках своей среды.
4. **Публичный сайт.** Публикуйте `apps/web` с отметкой Beta, описанием ограничений и приглашением тестеров. `registration_open` в `status.json` держите `false`, пока не пройдены проверки входа, изоляции арендаторов и приватности. Недоступность ещё не готовых функций должна быть явно показана в интерфейсе.
5. **Приёмка.** Из реальных MCP-клиентов (Claude Code, ChatGPT, Claude) проверьте OAuth, холодный старт и чтение; отдельно проверьте каналы и каждый заявленный файловый сценарий (критерии — [05_ACCEPTANCE.md](05_ACCEPTANCE.md)). После успешных тестов продвигайте именно проверенный артефакт и выполняйте внешние smoke-проверки. Статусы в `status.json` меняются только по результатам приёмки.
6. **Независимая установка.** Убедитесь, что копия в другом аккаунте Cloudflare работает на собственных Telegram- и OIDC-реквизитах: отсутствие чужого домена не должно ломать вход, шифрование, квоты и MCP.

## 5. Git, CI и preview

- Непроверенный PR (включая форки) получает только бессекретный CI: lint, типы, unit-тесты, проверки безопасности и синтетические фикстуры (`.github/workflows/ci.yml`). Без `pull_request_target`, без runner'ов рядом с production, без deploy, remote D1 и входа в Telegram.
- Review обязателен для изменений в auth, криптографии, миграциях, инфраструктуре и CI. Защиту веток проверяйте фактически, а не по наличию CODEOWNERS.
- Preview-сборки не получают production-адреса API и живые привязки. Staging использует отдельный origin, отдельные D1/DO/KV и секреты. Service Binding в preview Worker может указывать на production: проверяйте каждую привязку, имя Preview не доказывает изоляцию. [S16]
- Путь релиза: PR → CI → изолированный staging → review → продвижение конкретного SHA → контролируемые миграции → внешний smoke. Сборка UI не выполняет SQL.
- Production выпускается только через GitHub (`.github/workflows/deploy.yml`): push в `main` публичного репозитория → полный CI повторно → определение изменённых Workers → защищённое окружение `production` (только ветка `main`, ручное подтверждение мейнтейнером) → миграции D1 → deploy → внешний smoke. Токен Cloudflare и реальные ID ресурсов хранятся только в секретах окружения; конфиг с ID собирается в CI (`scripts/deploy/render-wrangler.mjs`) и не коммитится. Секреты Workers (KEK, HMAC, ключи сессий) остаются в Cloudflare и в workflow не попадают. Вывод wrangler в публичные логи не пишется. На машинах мейнтейнеров постоянного токена деплоя нет; ротация секретов Workers выполняется вручную с временным токеном.
- Любой может сверить: production собирается из конкретного коммита `main` этого репозитория, запуск и одобрение видны в истории Actions и Deployments.

## 6. Административный вход (OIDC)

`postun-admin` — отдельный Worker с собственной D1 и привязкой `CONTROL` к `postun-auth` (только приостановка/возобновление). Подробности — [06_ADMIN_OIDC.md](06_ADMIN_OIDC.md). Общие требования к провайдеру:

- Роли `postun.viewer`, `postun.operator`, `postun.owner`; роль проверяется при входе, а имя claim с ролями задаётся `ADMIN_OIDC_ROLES_CLAIM`.
- Конфиденциальный клиент (клиентский секрет хранится только в Cloudflare Secrets) с grant types `authorization_code` и `refresh_token`; PKCE S256; redirect URI вида `<ADMIN_ORIGIN>/oidc/callback`.
- Многофакторная проверка: по умолчанию ID-токен должен содержать значение `amr` из `ADMIN_MFA_AMR_VALUES` (`mfa,otp,hwk,swk,pop`); `ADMIN_REQUIRE_MFA_AMR=false` отключает проверку и допустим только осознанно.
- Клиент приложения не получает полномочий управлять всем провайдером.
- Обязательные параметры: `ADMIN_OIDC_ISSUER`, `ADMIN_OIDC_CLIENT_ID`, `ADMIN_OIDC_CLIENT_SECRET`, `ADMIN_OIDC_SCOPES` (строка scope должна давать refresh token и claim с ролями), `ADMIN_OIDC_ROLES_CLAIM`, `ADMIN_OIDC_ROLES_TENANT` и `ADMIN_OIDC_EXTRA_AUDIENCE` (для обоих допустимо литеральное `none`, чтобы явно отключить проверку), `ADMIN_SESSION_KEY`, `ADMIN_ORIGIN`. Пока значения не заданы, admin отвечает 503. Необязательные: `ADMIN_OIDC_CLIENT_AUTH` (`basic`|`post`), `ADMIN_OIDC_ID_TOKEN_ALG` (по умолчанию RS256).

## 7. Миграции, откат и ключи

- Ресурсы создаются один раз. Обычный deploy не пересоздаёт production D1/DO, не выполняет reset/reseed и не подставляет синтетических пользователей.
- Миграции схемы: expand → совместимый код → возобновляемый backfill → проверка → feature flag; contract — отдельным релизом. Перед изменением схемы проверяйте совместимость N/N+1 на непустой синтетической БД.
- Откат Worker не откатывает БД и Durable Objects. При восстановлении из резервной копии учитывайте записи, сделанные после неё, и состояние запретов/tombstone; нельзя возвращать ранее разрешённую сессию поверх более поздней блокировки.
- Резервная копия KEK (`SESSION_KEK`) должна храниться отдельно от Cloudflare. Потеря KEK делает сохранённые сессии нечитаемыми и потребует повторного подключения Telegram-аккаунтов; безусловное восстановление не гарантируется.

## 8. Допуск тестеров

Пока `REGISTRATION_OPEN=false`, новые профили создаются только для числовых Telegram ID из необязательного секрета `BETA_TESTER_TELEGRAM_IDS` (через запятую; сверяется с claim `id`, а не `sub`). Некорректный список выключает вход целиком (503). Существующие профили при этом входят как обычно.

## 9. Self-host: короткий путь

Fork/clone → собственные ресурсы Cloudflare по шаблонам → собственные Telegram-приложение и OIDC-реквизиты бота → собственные ключи шифрования → собственный OIDC-клиент для admin → миграции → тесты OAuth/MTProto/безопасности → собственные домены. Шаблоны не содержат production-идентификаторов. Для старта достаточно бесплатного плана Cloudflare; если измерения покажут необходимость платного плана, это решение принимается осознанно и с оценкой расходов, а не скрытым запасным путём.
