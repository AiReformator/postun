# 08. Postun Beta — проектные решения и исправленные противоречия

Документ фиксирует ключевые проектные решения и технические противоречия, которые были устранены в спецификации. Источники — в [07_SOURCES.md](07_SOURCES.md).

## 1. Принятые проектные решения

| Область | Решение |
|---|---|
| Название | Postun; публичный статус — Postun Beta |
| Администраторы | Вход через OIDC-провайдер администраторов + роли + MFA; не Telegram-вход и не статический пароль ([06_ADMIN_OIDC.md](06_ADMIN_OIDC.md)) |
| Пользователи | Telegram OIDC; доступ к переписке подтверждается отдельно через MTProto |
| Открытая часть | Весь исполняемый код, включая алгоритмы защиты и административный UI |
| Защищённая часть | Ключи, credentials, live-настройки доступа и пользовательские данные; в репозиторий не входят |
| OAuth storage | Поддерживаемый библиотекой Workers KV; без самодельных несовместимых token tables |
| Изоляция админки | Отдельная metadata D1 без vault/control/OAuth bindings |
| Эксплуатация | Free-first, без автоматического платного перехода; оценка стоимости по измерениям |
| Переносимость | Установка в собственный Cloudflare account со своим OIDC-провайдером администраторов, без зависимости от сервиса Postun |

## 2. Исправленные технические противоречия

Публичный исходный код не означает публикацию ключей. Скрытие алгоритма шифрования не используется как основная защита. Self-host не требует обязательного закрытого security package.

Сайт, Telegram sign-in, MTProto session и MCP OAuth — разные уровни. Успешный вход не означает разрешения на любой аккаунт. Административный OIDC-провайдер отделён от пользовательского входа и не получает Telegram-содержимого.

Управляемое облачное шифрование не обещает zero-knowledge. Оператор, контролирующий runtime и ключи, остаётся доверенной стороной. Администратор продукта и владелец инфраструктуры имеют разные возможности.

KV eventual consistency дополнена проверкой deny/version в authoritative DO. Отзыв доступа не считается мгновенным только потому, что token record удалён из KV. D1 и DO не объявляются общей транзакцией.

Одна логическая загрузка может состоять из нескольких HTTP Range-запросов. Поэтому download intent не уничтожается после первого GET, но привязан к владельцу, grant и сроку. Уже выданные байты невозможно отозвать.

Память ограничивается на isolate, а не на каждый HTTP-запрос. MTProto frames по открытому сокету не считаются автоматически отдельными HTTP subrequests. Ограничение 10 мс Free Worker не переносится механически на Durable Objects.

Поддержка файла до 512 МБ означает целевой потолок передачи, а не гарантированное вложение в любой ИИ-клиент. Активный лимит равен меньшему из проектного потолка и реально проверенного размера.

Preview URL не обеспечивает изоляцию service bindings и баз данных. Production release не пересоздаёт D1/DO namespaces и не генерирует новые ключи вместо действующих.

## 3. Границы серверных компонентов

Три серверных deployment оправданы разными правами: auth, MCP/vault и admin. Отдельная metadata DB предотвращает появление лишнего доступа у админки. Всё остальное остаётся модулями, а не отдельными сервисами. Собственная криптография не пишется: используются готовые OAuth/OIDC/MTProto-библиотеки. Если mtcute не работает в Workers, фиксируется точный технический blocker и проверяется ограниченный адаптер; перенос в другую инфраструктуру не выполняется молча.

## 4. Статус проверки

Технические ограничения сверены с первоисточниками из [07_SOURCES.md](07_SOURCES.md); это проверка документации, а не независимый аудит криптографии. Поведение конкретного развёртывания (аккаунт Cloudflare, DNS, OIDC-провайдер администраторов, реальные клиенты MCP, нагрузка, MTProto в Workers) подтверждается тестами и приёмкой самого развёртывания, а не этим документом. Актуальный статус функций — apps/web/status.json (на сайте — раздел #status).

Публичные страницы не заявляют независимый security-аудит, uptime SLA, отсутствие любых метаданных у провайдера или поддержку непроверенных клиентов. Участие бета-тестеров не позволяет отключать контроль доступа.
