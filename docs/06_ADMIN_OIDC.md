# 06. Postun Beta — вход администраторов через OIDC-провайдер

Административная часть (apps/admin) использует произвольного стандартного OIDC-провайдера и не привязана к конкретному вендору. Провайдер нужен только администраторам; пользовательский вход через Telegram и MCP OAuth Postun — отдельные потоки.

## 1. Конфигурация провайдера

Нужен отдельный server-side (confidential) OIDC-клиент для админки. Exact redirect URI: `https://<admin-host>/oidc/callback`; exact post-logout redirect: `https://<admin-host>/`. Для staging — отдельный клиент и свои URI; wildcard не использовать. Значение `<admin-host>` оператор задаёт переменной `ADMIN_ORIGIN` (только https, без пути).

Issuer берётся из реального deployment и проверяется через discovery (`/.well-known/openid-configuration`): обязательны authorization, token endpoints и JWKS. Если провайдер заявляет `code_challenge_methods_supported`, в списке должен быть S256, иначе вход закрыт.

Поток — Authorization Code + PKCE S256, одноразовые state и nonce. Метод клиентской аутентификации: `ADMIN_OIDC_CLIENT_AUTH=basic` (по умолчанию) или `post`. Алгоритм подписи ID token: `ADMIN_OIDC_ID_TOKEN_ALG` (по умолчанию RS256). Client secret хранится только как секрет Admin Worker. ID token не используется как API access token. [S12]

## 2. Конфигурационные параметры

| Имя | Назначение |
|---|---|
| ADMIN_OIDC_ISSUER | Issuer URL (https, без query/fragment) |
| ADMIN_OIDC_CLIENT_ID, ADMIN_OIDC_CLIENT_SECRET | Учётные данные клиента (secret — только через `wrangler secret`) |
| ADMIN_OIDC_SCOPES | Полная строка scopes без значения по умолчанию; должна обеспечивать refresh token и claim с ролями |
| ADMIN_OIDC_ROLES_CLAIM | Имя claim (в ID token или userinfo) с ролями администратора |
| ADMIN_OIDC_ROLES_TENANT | Обязательный. Ключ, который должен содержать значение каждой роли (ограничение организацией/проектом/тенантом); литерал `none` отключает проверку явно |
| ADMIN_OIDC_EXTRA_AUDIENCE | Обязательный. Значение, которое должно входить в `aud` ID token; литерал `none` отключает проверку явно |
| ADMIN_SESSION_KEY | 32 случайных байта (base64/base64url); шифрует refresh token в admin D1 |
| ADMIN_ORIGIN | Точный https-origin админки |
| ADMIN_REQUIRE_MFA_AMR | `true` по умолчанию; `false` отключает требование MFA |
| ADMIN_MFA_AMR_VALUES | Допустимые значения `amr` (по умолчанию `mfa,otp,hwk,swk,pop`) |
| ADMIN_OIDC_CLIENT_AUTH, ADMIN_OIDC_ID_TOKEN_ALG | См. §1 |

Шаблон: `apps/admin/.dev.vars.example`. Секреты задаются командой `npx wrangler secret put NAME` (значение через stdin/prompt) с собственным `CLOUDFLARE_API_TOKEN` оператора; в репозиторий они не попадают.

Fail-closed: если любое обязательное значение отсутствует, пусто или некорректно (не https, origin не совпадает, issuer с query/fragment, плохой ключ сессии), админка целиком отключена и отвечает 503. Проверки tenant и extra audience нельзя отключить пропуском или опечаткой, только литералом `none`.

## 3. Роли приложения

| Роль Postun | Полномочия |
|---|---|
| postun.viewer | Числа пользователей, связей, месячные агрегаты и статусы |
| postun.operator | То же + suspend/resume через отдельный ограниченный control endpoint |
| postun.owner | То же + настройки бета-квот |

Роли — прикладные, а не административные роли самого провайдера; администратор приложения не обязан владеть провайдером. Роли читаются из claim `ADMIN_OIDC_ROLES_CLAIM` (сначала ID token, затем userinfo). При заданном `ADMIN_OIDC_ROLES_TENANT` claim должен быть объектом (или массивом объектов), ключи которого — роли, а значение каждой роли — объект, содержащий этот ключ тенанта; роль вне нужного тенанта не засчитывается. При `none` допустим массив строк либо объект с ключами-ролями. Неизвестные роли игнорируются, при наивысшей из распознанных действуют её права. Email, домен и сам факт успешного входа не дают доступа; нет роли — 403, без fallback на общий allowlist.

Перед включением нужно проверить реальные подписанные claims на тестовом пользователе.

## 4. Вход и сессия

Admin Worker создаёт state, nonce и PKCE verifier, шифрует их в короткоживущий (10 минут) flow-blob в cookie `__Host-postun_admin_flow` и перенаправляет на провайдера. Callback принимается один раз (использованный state фиксируется в D1), затем проверяются: issuer (точное совпадение), audience (включая client_id и, если задано, extra audience), azp, nonce, exp/iat, настроенный alg и подпись по JWKS доверенного issuer. Токены другого issuer, с неожиданным alg или aud отклоняются.

После проверки выдаётся непрозрачная cookie `__Host-postun_admin`; ID, access и refresh tokens браузеру не передаются. Refresh token хранится в admin D1 в зашифрованном виде (AES-GCM, ключ `ADMIN_SESSION_KEY`, привязка к идентификатору сессии).

Параметры сессии (проектные, не defaults провайдера): idle 15 минут, absolute 60 минут, повторная проверка полномочий не реже 5 минут и перед каждой записью. Повторная проверка выполняет refresh_token grant и заново читает роли из нового токена (или userinfo); повторная проверка старого JWT отозванную роль не увидела бы. Роль отозвана или refresh отклонён — сессия уничтожается. Провайдер недоступен — запись блокируется (503), а не разрешается по устаревшим данным. Сессия без refresh token живёт не дольше 5 минут. Локальная блокировка subject и отзыв admin session действуют независимо от провайдера. Задержку отзыва нужно измерить на staging; если 5 минут не достигаются, сократить срок сессии.

## 5. MFA

По умолчанию вход требует в `amr` ID token хотя бы одно значение из `ADMIN_MFA_AMR_VALUES`; иначе 403. Это проверка заявленного провайдером результата, поэтому сама политика MFA/passkey настраивается у провайдера и проверяется реальным входом, в том числе восстановление доступа и отсутствие обхода через альтернативный flow. Параметр `prompt=login` вторым фактором не считается. Отключение (`ADMIN_REQUIRE_MFA_AMR=false`) допустимо только осознанно и не рекомендуется.

## 6. Защита запросов

Каждый запрос проверяет session и роль. Изменяющие запросы дополнительно требуют: точный Origin, свежую повторную проверку ролей, CSRF-токен в теле формы (сравнение за постоянное время) и достаточную роль (suspend/resume — operator и выше, квота — owner). Ответы отдаются с `cache-control: no-store` и строгой CSP (`default-src 'none'`, `frame-ancestors 'none'`). Нет локального пароля, общего статического токена и Telegram-fallback. Cloudflare Access допустим как дополнительный барьер, но не заменяет серверную авторизацию.

## 7. Что видит администратор и наименьшие привилегии

Псевдонимный ID владельца, число связанных аккаунтов, статус, beta_free, success_count/out_bytes за месяц, общие классы ошибок. Не показываются переписка, номера телефонов, список читаемых каналов, документы, имена файлов, OAuth или MTProto secrets. Операции «войти как пользователь» нет. Действия администраторов пишутся в аудит без содержимого.

Admin Worker имеет только два binding: собственную admin metadata D1 и service binding `CONTROL` к отдельной точке входа `AdminControl` с фиксированной схемой агрегатов и ограниченными командами suspend/resume. Bindings к Control D1, OAuth KV и SessionAndQuotaDO отсутствуют; `AdminControl` не публикуется как HTTP route.

## 8. Самостоятельная установка

Self-hoster подключает собственного OIDC-провайдера и задаёт его issuer, client, claim ролей и остальные параметры из §2. Без них админка выключена (503) и не открывает доступ; пользовательский MCP работает независимо.

## 9. Обязательная приёмка

Нет session — отказ; пользователь без роли — 403; чужой issuer, tenant или audience — отказ; отсутствие или недопустимое значение любого обязательного параметра — админка закрыта; значение `none` отключает только соответствующую проверку; нет MFA в `amr` — 403; отозванная роль — блокировка в измеренный срок; повтор callback и истёкший flow — отказ; CSRF или чужой Origin — отказ; admin не может достать vault по bindings; logout завершает локальную session; секреты отсутствуют в публичной сборке и браузере. Идентификаторы тестов — AD-01…AD-04 в [05_ACCEPTANCE.md](05_ACCEPTANCE.md).
