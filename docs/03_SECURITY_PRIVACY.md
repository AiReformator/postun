# 03. Postun Beta — безопасность и приватность

**Редакция 2.0-beta.** Это технический контракт защиты для экспериментального сервиса. Бета-статус не разрешает отключать защиту ради быстрого запуска.

## 1. Открытая и непубличная части

| Объект | Публичный репозиторий | Защищённое размещение |
|---|---|---|
| MCP, OAuth-интеграция, OIDC, RBAC | Полный исходный код | Нет обязательного закрытого дубликата |
| Шифрование и проверки ownership | Код, алгоритмы, тесты, форматы envelope | Только значения ключей — в Secrets |
| Админ-панель и адаптер OIDC-провайдера администраторов | Полный код и пример настройки (.dev.vars.example) | Реальные назначения ролей, client secret, идентичности операторов |
| Cloudflare конфигурация | Шаблоны и безопасные defaults | Production resource inventory, access policy и deploy credentials |
| Telegram-сессии и персональные данные | Никогда | Зашифрованный runtime storage |
| Статистика пользователей | Только синтетические fixtures | Минимальные агрегаты в нашем Cloudflare |
| Incidents и необъявленные уязвимости | Исправления и согласованные advisories | Детали до исправления, адресация и recovery evidence |
| Будущие платежи | Интерфейсы и код по выбранной модели лицензии | Секреты, персональные и финансовые записи |

«Закрытая часть ключевой безопасности» означает ключевой материал и операционные доступы, а не скрытый алгоритм. Self-host должен получать всю необходимую защиту. Публичный код не содержит обращения к нашему серверу для расшифрования или включения безопасности. Точные resource IDs не являются криптографическими секретами, но реальные deployment inventory и assignments не публикуются без необходимости.

Приватный Git-репозиторий допустим для не содержащих секретов production manifests, но не является хранилищем токенов. Реальные секреты задаются через Cloudflare Secrets (`npx wrangler secret put NAME` с собственным CLOUDFLARE_API_TOKEN оператора); резервные ключи — вне Git и вне общедоступных артефактов. [S09]

## 2. Модель доверия

Сервису доверяют выполнять только разрешённую операцию. В облачном режиме runtime видит session key и возвращаемое содержимое в памяти. Оператор с правами менять runtime или секреты технически способен расширить доступ. Шифрование at rest не превращает Postun в zero-knowledge или сквозной канал Telegram—ИИ.

Администратор продукта отличается от администратора Cloudflare. Первый не должен читать переписку даже через специально составленный запрос; второй обладает инфраструктурными правами и остаётся частью доверительной модели. Не обещать пользователю обратного.

## 3. Ключи и шифрование

Выбран один протокол: случайный 256-битный DEK на linked account; session ciphertext — AES-256-GCM; DEK обёрнут KEK через WebCrypto AES-GCM с отдельным nonce и purpose в AAD. Nonce 96 бит генерируется криптографически и не переиспользуется для одного ключа. AAD связывает principal_id, account_id, envelope_version, key_version и тип payload.

KEK доступен только MCP Worker/DO. Отдельные secrets для identity HMAC и web/admin sessions; ключи разных назначений не переиспользуются. В D1 нет session plaintext или KEK. Для rotation допускается ограниченное окно старого key_version; после rewrap и проверки старый ключ отзывается по плану.

Удаление ciphertext и wrapped DEK из текущей БД не доказывает мгновенное удаление из резервных копий. Надёжный отзыв — блокировка grant/account и завершение соответствующей Telegram-сессии. Если Telegram недоступен, показываем revocation pending и не продолжаем использовать ключ. После восстановления старого backup не активировать отключённые подключения автоматически.

## 4. Разрешённое хранение

| Категория | Целевая retention-политика беты |
|---|---|
| Identity и подтверждённые связи | Пока профиль активен; удаление по запросу с учётом срока backup |
| Session envelope | Пока аккаунт подключён; без экспорта через UI |
| OAuth grants / hashed tokens | По lifecycle провайдера, с expiry и отзывом |
| Месячные success_count / out_bytes | Текущий месяц + 2 предыдущих; дальнейшее хранение — отдельное решение |
| Идемпотентные operation IDs | До 24 часов; без аргументов и содержимого результата |
| Login state / QR / download intent | Минуты, согласно конкретному протоколу и сроку Telegram token |
| Административные security-события | 30 дней: actor, action_code, target_opaque_id, outcome, time |
| Сообщения, поисковые фразы, документы | Не сохраняются; только bounded volatile buffers |
| Номер телефона, username, имя файла в истории | Не сохраняются по умолчанию |

Это проектные сроки, а не подтверждение уже работающего удаления. Их надо реализовать и испытать. Пользовательские журналы запросов не вести. Служебный аудит администратора не скрывать под заявлением «вообще никаких логов».

Workers Logs, traces, Tail и внешняя телеметрия с пользовательскими payload выключены. Вызовы SDK не должны писать raw error, Telegram payload, QR token, cookie или URL capability. Observability config проверять для каждой среды, а не только в примере Wrangler. Метрики чисел/классов ошибок без аргументов допустимы. У Cloudflare и OIDC-провайдера администраторов возможны собственные инфраструктурные метаданные; приложение не обещает их отсутствия. [S10]

## 5. Контроль доступа и сетевые барьеры

Каждый MCP-вызов: валидный Postun OAuth -> актуальный grant/deny state -> принадлежность аккаунта -> chat/account allowlist -> квота -> upstream. Scope-метаданные MCP не заменяют серверную проверку. При ограничении конкретными чатами нельзя сначала вернуть глобальный результат, а затем надеяться на фильтрацию ИИ.

Сайтовые сессии и MCP grants не дают административных прав. Сессия OIDC-провайдера администраторов не является Telegram-сессией. В серверных методах не принимать principal из браузера как доверенное поле. D1 SQL параметризован; разрешены только заранее описанные DTO и колонки.

OIDC/OAuth: exact issuer/audience/redirect; PKCE S256, state, nonce, anti-replay, проверка подписей и срока. Cookie: __Host- prefix, Secure, HttpOnly, Path=/, без Domain; SameSite определяется проверенным redirect-flow. Токены не хранятся в localStorage. CORS — точные origins, credentialed wildcard запрещён. Browser POST защищён CSRF. [S01–S04, S11]

Исходящие назначения ограничены Telegram, выбранным IdP и подтверждёнными MCP client metadata/JWKS. Запрет произвольного fetch URL, private/loopback/link-local/metadata адресов и небезопасных redirects. Для CIMD использовать актуальные SSRF-защиты OAuth SDK, а не свой парсер.

## 6. Ресурсная безопасность

До скачивания проверять размер. Ограничить concurrent transfers и буферы на isolate, а не только на один request. Передача 512 МБ не требует 512 МБ RAM, но криптографию и декодирование надо измерить. FloodWait не обходить новым аккаунтом или повторным штормом; сохранять минимальный retry-after state и возвращать понятную ошибку.

Не сохранять исходные ответы ради идемпотентности. Повтор с тем же operation_id может заново читать Telegram, но не повторно списывать уже завершённую логическую операцию в пределах TTL. Для потоков считать выданные байты; completion сервера не доказывает сохранение файла у клиента.

Сообщения Telegram — недоверенные данные. Не интерпретировать их как инструкции сервера, не менять scopes и не выдавать секреты. Read-only предотвращает запись в Telegram, но само по себе не гарантирует защиту от избыточного чтения: необходимы account/chat ACL и ограничение объёма.

## 7. Supply chain и открытая разработка

Публичные PR: secretless CI, синтетика, изолированные runners, отсутствие production bindings. Не исполнять untrusted checkout через pull_request_target. Lockfile и action refs фиксируются; изменения auth, crypto, infra и CI требуют review. Лицензии зависимостей проверяются до включения кода.

Код выпускается под выбранной открытой лицензией; рекомендуемый default — Apache-2.0 после проверки совместимости. Пока LICENSE фактически не добавлен, наличие публичного репозитория не обозначать как завершённое лицензирование.

При утечке сначала revoke/rotate, затем чистка истории; удаление строки из Git само по себе не восстанавливает секретность. Публичные issue не должны содержать реальные tokens, screenshots кабинета с сессиями или переписку.

## 8. Проверяемые инварианты

A не читает B; admin не читает session store; stale OAuth KV не отменяет deny; preview не получает production keys; stream не создаёт persisted file; browser и CI не получают secrets; независимый self-host работает без Postun SaaS. Все инварианты имеют отрицательные тесты в 05_ACCEPTANCE.md.
